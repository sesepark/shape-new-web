# Vercel · Render · Neon 무료 운영 기준

## 배치

- Vercel: `shape_web/frontend` Next.js 앱
- Render: `shape_web/backend` FastAPI 앱
- Neon: PostgreSQL pooled connection URL

## 필수 안전 설정

- Render 환경 변수에서 `DB_POOL_SIZE=2`, `DB_MAX_OVERFLOW=1`을 유지합니다. 20명 규모에서 연결 수를 작게 유지해 Neon 무료 한도를 보호합니다.
- 공개 데이터는 **두 겹**으로 지킵니다. 앞은 Next.js Data Cache(`revalidate: 3600`), 뒤는 백엔드 안의 공개 응답 캐시(`public_cache_seconds=3600`, `app/cache.py`)입니다. 운영진이 저장하면 백엔드가 자기 캐시를 버리고 `/api/revalidate`로 앞단까지 즉시 새로 고치므로, 한 시간이라는 값은 **관리자 화면을 거치지 않고 바뀐 경우의 예비 장치**일 뿐입니다. 이 재검증 경로가 끊기지 않게 유지합니다.
- **두 창의 길이는 같아야 합니다.** 어긋나면 데이터베이스를 깨우는 시점이 흩어져서 아래 Neon 항목에서 얻는 것이 대부분 사라집니다.
- 백엔드 캐시는 시계에 고정된 창으로 만료됩니다. Neon 요금은 질의 횟수가 아니라 깨어 있는 시간이라, 열 건을 한꺼번에 처리하는 것이 한 건씩 흩어 처리하는 것보다 훨씬 쌉니다.
- 다만 **정확히 같은 순간에 만료시키지는 않습니다**(`cache_spread_seconds=30`). 그러면 그 순간이 곧 부하가 됩니다. Neon 은 5분을 놀아야 잠들므로 30초 안에서 흩어도 '한 번 깨어남' 은 그대로이고, 서버에는 몰리지 않습니다.
- **같은 창구는 하나만 채웁니다**(`cache.lock_for`). Vercel 이 여러 지역에서 같은 쪽을 동시에 재검증하므로, 묶지 않으면 동시 8건이 질의 24건이 됩니다(실측). 연결이 셋뿐인 무료 인스턴스에서는 그대로 줄서기가 됩니다.
- **게시판·관리자·마이페이지는 캐시 대상이 아닙니다.** 세션 쿠키가 실린 요청은 무조건 `private, no-store` 이고 캐시를 아예 비켜 갑니다. 관리자 화면이 공개 창구(`/pages/*`)를 읽을 때도 쿠키를 실어 보내 캐시를 지나가게 합니다 — 고치려고 여는 화면이 캐시를 거치면 옛 값 위에 덮어쓸 수 있습니다.
- **긴 창은 무효화가 확실할 때만 안전합니다.** `refresh()` 는 실패하면 한 번 더 두드리고, 비밀값이 어긋난 경우(401·403·503)는 재시도 대신 바로 로그를 남깁니다. 이 경로가 조용히 끊기면 한 시간짜리 지연이 진짜 지연이 됩니다.
- 응답 캐시 헤더는 허용 목록 방식입니다. `/pages/*`, `/news*`, `/equipment*`, `/roadmap`, `/links`, `/push/public-key`, `/member-profiles`, `/shape-up`만 공유 캐시를 쓰고, 그 밖의 응답(세션·알림·게시판·예약·관리자)은 모두 `private, no-store`로 내려갑니다.
- **세션 쿠키가 실린 요청은 공개 읽기라도 `private, no-store`로 내려갑니다.** `/shape-up` 처럼 같은 주소인데 보는 사람에 따라 `canEdit`이 달라지는 응답이 있어, 앞으로 공유 캐시를 붙이더라도 남의 화면에 수정 버튼이 뜨지 않습니다.
- 예약 가능 시간(`/equipment/{id}/availability`)은 승인 즉시 바뀌므로 `volatile_cache_seconds=30` 으로 짧게 둡니다.
- API 응답은 500바이트를 넘으면 gzip으로 압축합니다. 한글 JSON은 `\uXXXX`로 나가서 55~68% 줄어듭니다. 앞단에 프록시가 없으므로 압축은 앱이 직접 합니다.
- API는 분당 공개 읽기 120회, 쓰기 20회로 제한합니다. **로그인한 회원은 계정별로, 그 밖에는 주소별로 셉니다.** 학교 Wi-Fi처럼 여러 명이 한 주소를 나눠 쓰는 곳에서 서로의 한도를 깎지 않게 하기 위해서입니다. 요청 본문은 2MB를 넘으면 데이터베이스 접근 전에 거절합니다.
- 공지 푸시는 스레드 풀로 보내고 커밋 이후에 실행합니다. 동기 라이브러리를 요청 안에서 그대로 돌리면 워커 하나짜리 무료 인스턴스가 전송 시간만큼 통째로 멈춥니다.
- **목록을 돌려주는 창구에는 반드시 개수 상한을 둡니다.** 게시판 30, 자료실 40, SHAPE UP 60, 로드맵 200, 링크 100입니다. 게시판·자료실은 `before=` 로 이어받고 화면에 '더 보기'가 있습니다. 상한 없는 `select(...).all()` 은 학기가 쌓이는 만큼 응답이 무거워집니다.
- **개수를 끊을 때 어느 쪽을 남기는지 확인합니다.** 로드맵은 시작일 오름차순이라 앞에서 끊으면 잘려 나가는 쪽이 **미래**이고, 홈의 '일정' 칸이 조용히 빕니다. 최신 쪽에서 끊고 돌려줄 때 다시 오름차순으로 맞춥니다. 게시판·자료실·SHAPE UP 은 최신순이라 그대로 앞에서 끊으면 됩니다.
- **목록 응답에 본문을 싣지 않습니다.** 본문은 상세 창구에서만 나갑니다. 상세 응답도 화면이 실제로 쓰지 않는 칸은 빼세요(`ShapeUpDetailRead` 가 편집기용 `content_json` 을 싣고 있었습니다).
- **무언가를 지우거나 갈아 끼울 때 Cloudinary 원본도 함께 지웁니다**(`app/services/cloudinary.py`). 자료실·장비·소식·SHAPE UP·프로필 사진이 모두 이 길을 지납니다. 이건 용량 문제이기 전에 **지운 사진이 안 지워지는 문제**입니다 — 남은 파일은 공개 주소로 계속 열립니다.
- **본문에 박힌 사진은 지우는 자리에서 건드리지 않습니다.** 같은 사진이 다른 글에도 붙어 있을 수 있어, 모든 글을 훑어 본 뒤에야 판단할 수 있습니다. 아래 정리 스크립트가 맡습니다.
- **사진은 저장 버튼보다 먼저 올라갑니다.** 편집기에서 파일을 고르는 순간 브라우저가 Cloudinary 로 바로 보냅니다. 그래서 쓰다 만 글, 뺀 사진, 갈아 끼운 사진이 전부 주인 없는 파일로 남습니다. 배포 첫날에 재어 보니 `shape/` 자산 35개 중 **21개(60%)** 가 그랬습니다.
- **주인 없는 파일은 여섯 시간에 한 번 정리합니다**(`app/services/media_sweep.py`, `media_sweep_seconds`). 크론을 두지 않고 들어오는 요청에 얹어 확인합니다 — 크론을 흉내 내려고 서버를 주기적으로 깨우면 Neon 이 그만큼 깨어 있어야 합니다. 확인 시각이 공개 캐시가 새로 채워지는 때와 겹치므로 대개 이미 깨어 있는 데이터베이스를 씁니다. 조용한 새벽에는 서버가 잠들어 있어 아예 돌지 않고, 그때는 `scripts/sweep_orphan_media.py` 를 직접 돌립니다(기본은 목록만, `--apply` 로 삭제).
- **정리가 주소를 뽑는 일은 데이터베이스 안에서 합니다**(Postgres 일 때). 한 번 돌 때마다 여덟 개 표를 조건 없이 훑고 거기에는 모든 글의 본문이 들어 있어서, 예전처럼 본문을 통째로 실어 오면 글이 쌓이는 만큼 그대로 무거워집니다(1,500편 규모에서 회당 약 7 MB, 한 시간에 한 번이면 한 달 5 GB — Neon egress 한도 전부). 밖으로 나오는 것이 찾아낸 주소 몇십 건뿐이 되도록 `regexp_matches` 로 데이터베이스 쪽에서 뽑습니다. **주소를 알아보는 정규식은 `URL_PATTERN` 하나를 파이썬과 Postgres 가 같이 씁니다** — 두 벌로 두었다가 한쪽만 고치면 쓰이고 있는 사진이 고아로 판정되어 지워집니다. SQLite(로컬·시험)는 예전대로 파이썬에서 뽑습니다.
- **한 건도 못 뽑았는데 본문에 주소가 있으면 정리를 건너뜁니다.** 뽑는 쪽이 고장 났다는 뜻이고, 그대로 두면 쓰이는 사진이 전부 지워집니다. 정리를 거르는 쪽이 언제나 안전합니다.
- **주기를 더 늘리지 않는 이유.** 이 시계는 프로세스 안에 있고 무료 인스턴스는 15분만 놀아도 잠들어, 깨어날 때마다 0 부터 다시 갑니다. 하루로 두면 서버가 하루를 내리 깨어 있는 날이 없어 자동 정리가 사실상 한 번도 돌지 않습니다.
- **정리가 건드리지 않는 두 가지.** ① **예약 사용 전·후 사진**(`shape/reservation/`) — 장비를 누가 어떤 상태로 쓰고 돌려놓았는지는 활동 기록이라 예약이 지워져도 남깁니다. ② **올라온 지 하루가 안 된 파일**(`media_orphan_grace_hours`) — 방금 올렸지만 아직 저장을 안 누른 파일과 주인 없는 파일은 구별할 수 없습니다.
- 예약은 180일 이내·1회 12시간 이내만 접수하고, 승인 슬롯은 데이터베이스 고유 제약으로 중복을 막습니다. 이미 확정된 시간은 신청 단계에서 먼저 거절합니다.
- 홈 화면 로봇 3D는 선택한 모델만 먼저 내려받고 나머지는 브라우저가 한가할 때 미리 받습니다. 데이터 절약 모드나 2G에서는 미리 받지 않습니다. 네 모델 합계는 약 1.4MB이고 1년 `immutable`로 캐시됩니다.
- **올리기 전에 브라우저에서 줄입니다**(`lib/upload.ts`). 긴 변 1600px(장비·소식은 2000px), WebP 품질 0.82. 여기서 줄이면 올리는 사람의 데이터·Cloudinary 저장 용량·나중의 전송량이 한꺼번에 줄어듭니다. **PNG 는 크기와 상관없이 바꿉니다** — 무손실이라 작아도 크게 줄고(실측 267KB → 67KB), 화면 캡처와 안드로이드 기본 저장이 PNG 로 나옵니다. 이미 압축된 JPEG 만 300KB 아래에서 건너뜁니다.
- 사진은 대역폭에서 가장 큰 몫입니다. Cloudinary 주소는 `f_auto,q_auto,c_limit,w_*`로 내려가고, 그 밖의 주소(옛 사이트에서 옮겨 온 부원 사진)는 Next.js 이미지 최적화를 거칩니다. 원본을 그대로 내보내면 부원 페이지 한 번에 18MB가 나가고 Vercel 무료 100GB가 월 5,700뷰에 소진됩니다. 새 사진을 `public/figs`에 넣을 때는 긴 변 1600px 이내로 줄여 넣습니다.
- **부원 카드 사진은 카드가 가까워졌을 때 붙입니다.** `next/image` 는 기본이 lazy 지만 브라우저가 잡는 여유 범위가 넓어, 서른 장이 넘는 격자에서는 스크롤하지 않아도 대부분이 내려받아집니다(측정: 24장 중 18장). 첫 화면 몫 여덟 장만 처음부터 그리고 나머지는 400px 앞에서 붙이므로, **부원이 늘어도 첫 화면 비용은 그대로입니다.**
- **링크는 마우스를 올렸을 때만 미리 받습니다**(`HoverPrefetchLink`). 머리글과 전체 메뉴에 사이트의 거의 모든 주소가 들어 있어, 기본 동작대로 두면 한 쪽을 열 때마다 40건 넘는 프리페치가 나갑니다. 무료 요금제에서 가장 먼저 차는 것은 전송량이 아니라 **요청 수**입니다. 머리글이나 메뉴에 링크를 새로 넣을 때는 `Link` 대신 `HoverPrefetchLink` 를 씁니다.
- Vercel과 Render에서 자동 확장 상한 또는 지출 한도를 설정할 수 있으면 최소값으로 설정하고, 사용량 알림을 활성화합니다.

### 100~200명이 되면

Neon 은 질의 횟수가 아니라 **깨어 있는 시간**으로 셉니다. 5분을 놀아야 잠들므로
비용은 곧 '5분 간격이 끊기지 않고 이어지는 시간대의 총합' 이고, 이 값은 사람 수에
비례해 늘지 않고 **포화**합니다 — 대신 활동 시간대 전체를 덮습니다. 운영진
대여섯 명이 이미 하루의 41% 를 덮고 있으니, 부원 150명이면 하루 16~20시간,
월 120~150 CU-시간으로 **한도를 넘깁니다.** 넘으면 요금이 붙는 것이 아니라
**다음 달까지 데이터베이스가 정지**합니다.

여기서 나오는 결론이 하나 있습니다. **질의를 빠르게 만들어도 이 숫자는 줄지
않습니다.** 줄이려면 데이터베이스를 건드리는 '5분 창' 의 개수를 줄여야 하고,
공개 캐시가 이미 그 일을 합니다(비로그인 방문은 데이터베이스를 아예 건드리지
않습니다). 남은 것은 **로그인한 회원의 요청**인데 지금은 전부 캐시를 비켜 갑니다.
| Vercel | — | 사용량 API 가 Pro 전용이라 미측정 | | | |

> **이 숫자는 배포 첫날 것입니다.** Neon 프로젝트를 만든 지 26시간밖에 되지 않았고,
> 그 안에 마이그레이션·시드·여러 번의 배포·직접 확인이 들어 있습니다. 특히 Render 는
> **뜰 때마다 `alembic upgrade head` 를 돌리므로 배포 한 번이 곧 Neon 깨우기 한 번**
> 입니다. 그러니 아래 64% 는 평상시 값이 아니라 **위쪽으로 치우친 값**으로 보세요.
> 구조적 원인(5분 주기 ↔ 5분 자동 절전)은 분명하지만, 수치는 평상시로 며칠 지낸 뒤
> 다시 재야 합니다. 재는 법은 이 절 끝에 있습니다.

**이용자 다섯 명으로 이미 Neon 한도의 64% 를 쓰고 있었습니다.** 다른 어느 항목도
2% 를 넘지 않는데 이것만 그렇습니다. 이유는 요청량이 아니라 시간입니다.

- Neon 무료 compute 는 **100 CU-시간**이고 우리 endpoint 는 최소 0.25 CU 이므로,
  한 달에 **400시간(하루 13.1시간)** 만 깨어 있을 수 있습니다.
- Neon 은 **5분** 놀면 잠드는데, 예전 재검증 주기도 정확히 **5분**이었습니다.
  방문이 5분에 한 번만 이어져도 재검증이 백엔드를 부르고, 그 질의가 잠들기 직전의
  타이머를 되살립니다. 그래서 다섯 명만으로도 전체 시간의 33% 를 깨어 있었습니다.
- 넘으면 요금이 붙는 것이 아니라 **다음 달 1일까지 데이터베이스가 정지**합니다.
  즉 무료 티어의 위험은 청구서가 아니라 **정지**입니다.

그래서 재검증 주기를 한 시간으로 늘리고 백엔드 앞에 창 캐시를 두었습니다. 이 두
가지를 **함께** 해야 효과가 납니다. 주기만 늘리면 깨우는 횟수만 줄고 시점은 그대로
흩어져 있어, 한 번 깨울 때마다 최소 5분씩 붙잡히는 것은 변하지 않습니다.

### 야간을 넣어 다시 계산하면

Neon 은 **누가 부를 때만** 깨어납니다. Next.js 재검증은 방문이 있어야 일어나고
Render 는 15분이면 잠들므로, 아무도 안 들어오는 새벽은 값이 들지 않습니다. 문제는
검색 크롤러처럼 드문드문 들어오는 요청인데, 이때 재검증 주기가 그대로 값이 됩니다.

한국 시간 기준 활동 16시간 / 조용한 8시간으로 잡으면:

| | 5분 주기 (이전) | 1시간 주기 (지금) |
|---|---|---|
| 조용한 8시간 (크롤러만) | 사실상 8시간 내내 깨어 있음 | 시간당 1회 × 5.5분 = **44분** |
| 활동 16시간 (공개 페이지 몫) | 16시간 내내 | 16회 × 5.5분 = **1.5시간** |
| 하루 합계 (회원 활동 제외) | 약 24시간 | **약 2.2시간** |
| 월 환산 | 182 CU-시간 (한도의 182%) | **17 CU-시간** |

**바뀐 것의 효과가 가장 크게 나는 곳이 밤입니다.** 예전에는 크롤러 한 번이 5분을
사면 그다음 5분에 또 사서 밤새 이어졌는데, 지금은 한 시간에 한 번으로 끊깁니다.

남는 것은 **회원 활동**입니다. 로그인한 회원은 쪽을 열 때마다 `/auth/me` 로
데이터베이스를 건드리고 이건 캐시할 수 없습니다. 회원 활동이 하루 6시간에 걸쳐
흩어져 있다면 6시간 + 위의 2.2시간 = 8.2시간/일 → 월 **61 CU-시간**. 10시간에
걸쳐 흩어지면 월 **86 CU-시간** 으로 빠듯해집니다. 200명에서 남는 위험은 여기
하나이고, 다음 수는 상태·권한을 세션 토큰에 담아 `/auth/me` 가 데이터베이스를
건드리지 않게 하는 것입니다.

### 평상시 사용량을 다시 재는 법

Neon 은 소비량을 결제 주기 동안 **누적**해서 들고 있으므로, 두 시점에 읽어
빼면 그 사이의 실제 사용량이 나옵니다. 무료 요금제는 `consumption_history`
창구가 막혀 있어 이 방법을 씁니다.

```bash
source ~/Projects/SHAPE/service-tokens.txt 2>/dev/null   # 또는 값을 직접 넣습니다
curl -s -H "Authorization: Bearer $NEON_API_KEY" \
  "https://console.neon.tech/api/v2/projects/$NEON_PROJECT_ID" \
  | jq '.project | {consumption_period_start, active_time_seconds, compute_time_seconds}'
```

`compute_time_seconds ÷ 3600` 이 쓴 CU-시간, `active_time_seconds` 가 깨어 있던
시간입니다. 평상시로 사나흘 지낸 뒤 두 번 재서 차이를 보세요.

## 관리자 › 시스템 › 서버 탭

사용량을 사람이 직접 API 로 뽑지 않아도 되도록, 관리자 페이지에 **'서버' 탭**을
두었습니다(owner 만 보입니다). 이번 주기의 한도 대비 사용량, 기간 말 예상,
30일 환산, 그리고 이 속도면 언제 바닥나는지를 함께 보여 줍니다.

**서비스마다 '한 달' 이 다르므로 주기를 카드마다 밝힙니다.** 이 구분을 뭉뚱그리면
남은 여유를 잘못 읽게 됩니다.

| 서비스 | 주기 | 초기화 |
|---|---|---|
| Neon | 달력 월 (UTC) | 매월 1일. 소비 기간의 시작·끝을 API 가 직접 알려 주므로 추측하지 않습니다. **첫 기간은 프로젝트를 만든 날부터라 30일보다 짧습니다.** |
| Render | 달력 월 | 매월 1일. 인스턴스 시간 750과 대역폭. |
| Cloudinary | **최근 30일 이동창** | 초기화되는 날이 없습니다. 지금 값이 곧 지난 30일 합계이고, 하루가 지나면 가장 오래된 하루가 빠집니다. 저장 용량만은 지금 이 순간의 총량입니다. |
| Vercel | **최근 30일** | Hobby 는 청구 주기가 없고, 한도를 넘기면 30일이 지나야 풀립니다. |

Neon 처럼 기간이 짧을 때는 '기간 말 예상' 과 '30일 환산' 이 크게 벌어집니다
(실측 22% 대 76%). 한도가 실제로 걸리는 것은 앞이지만 계획에 쓰는 것은 뒤라,
둘 다 보여 주고 색은 급한 쪽을 따릅니다. **이동창인 서비스에는 예상치를 내지
않습니다** — 지금 값이 이미 한 달치라 거기에 배수를 곱하면 없는 사용량을 지어내는
것이 됩니다.

### 이 화면이 사용량을 늘리지 않게 하는 세 가지

- **데이터베이스를 건드리지 않습니다.** 부르는 곳은 각 서비스의 관리용 API 이고,
  Neon 콘솔 API 는 데이터베이스가 아니라 그 앞의 **제어면**이라 잠들어 있는
  compute 를 깨우지 않습니다. 이 창구가 데이터베이스를 여는 것은 로그인 검사
  뿐인데, 운영진이 관리자 화면을 여는 순간 어차피 일어나는 일입니다.
  `usage.snapshot()` 이 인자를 받지 않는 모양을 시험이 못 박고 있습니다.
- **시계를 두지 않습니다.** 크론이나 주기적 수집이 있으면 아무도 안 볼 때도 서버가
  깨어 있어야 하고, 그 시간이 Neon 한도에서 가장 먼저 닳습니다. 탭을 열 때만 모읍니다.
- **여섯 시간 동안 들고 있습니다**(`usage_cache_seconds`). 탭을 하루에 몇 번 열든
  바깥으로 나가는 요청은 그대로입니다. 화면의 '다시 모으기' 로만 당깁니다.

### 열쇠

`NEON_API_KEY` 는 **프로젝트 범위 키**입니다. Neon 은 읽기 전용 키를 주지 않아서
계정 전체 권한 키를 백엔드에 넣으면 그 키로 다른 프로젝트까지 지울 수 있습니다.
프로젝트 하나로 범위를 좁힌 키를 따로 만들어 넣었고, 그 밖의 호출은 실제로
거부되는 것을 확인했습니다(계정 프로젝트 목록·조직 API 키 조회 모두 거부).
그래도 **이 프로젝트 자체는 이 키로 지울 수 있으므로** owner 에게만 엽니다.

`RENDER_API_KEY` 는 **일부러 넣지 않았습니다.** Render 는 계정 전체 권한 키만
주는데, 그 대가로 얻는 것이 대역폭과 메모리뿐입니다. 넣으면 '서버' 탭에 Render
카드가 함께 뜹니다.

### endpoint 설정 — 0.25 CU 로 고정해 두었습니다

`autoscaling_limit_min_cu` 와 `autoscaling_limit_max_cu` 를 **둘 다 0.25** 로
맞춰 두었습니다(프로젝트 기본값도 같이). 예전에는 상한이 **2** 로 열려 있었는데,
한도가 '시간' 이 아니라 'CU-시간' 이라 부하가 몰려 1~2 CU 로 올라가면 같은
시간에 **네 배에서 여덟 배**를 씁니다. 한 달치를 며칠 만에 태울 수 있는
자리였습니다.

대가는 갑작스러운 부하에서 데이터베이스가 느려지는 것뿐입니다. 앞단의 Render
무료 인스턴스가 0.1 CPU 라 그만한 부하가 애초에 데이터베이스까지 가지 않습니다.

```bash
curl -s -H "Authorization: Bearer $NEON_API_KEY" \
  "https://console.neon.tech/api/v2/projects/$NEON_PROJECT_ID/endpoints" \
  | jq '.endpoints[] | {autoscaling_limit_min_cu, autoscaling_limit_max_cu}'
```

## cookierunhub 에서 가져온 것과 가져오지 않은 것

캐시와 비용 구조는 `~/Projects/cookierunhub` 를 참고합니다. 다만 그쪽은 집서버
한 대에 Caddy 를 세우고 대규모 트래픽을 받는 구조라, 장치를 그대로 옮기면 스무 명
규모의 무료 티어에는 과합니다. 판단 근거를 남겨 둡니다.

가져온 것

- **서버 안 TTL 캐시(`src/cache.py`)**. 처음에는 "스무 명 규모엔 과하다"며 일부러
  뺐는데, 실측해 보니 그 판단이 틀렸습니다. 문제는 질의가 많은 것이 아니라 Neon 이
  **깨어 있는 시간**으로 값을 매긴다는 것이었습니다. 다만 그쪽은 집서버라 잠들
  걱정이 없어 평범한 TTL 이면 충분했고, 우리는 만료 시점을 한데 모으는 창이
  필요했습니다(`app/cache.py`).
- **인증된 요청은 공유 캐시에서 제외**합니다. 그쪽 미들웨어가 인증 헤더를 보고
  곧바로 `private, no-store` 로 빠지는 것과 같은 장치입니다. 경로 목록만으로
  캐시를 결정하는 방식이 안전해지는 핵심입니다.
- **응답 압축**. 그쪽은 Caddy 의 `encode zstd gzip` 이 맡지만 우리는 Render 가
  uvicorn 으로 바로 들어와 앞단이 없으므로 앱에서 직접 합니다.
- **경로 접두사 → 캐시 수명 표**와 허용 목록 방식. 이미 같은 구조입니다.
- **사진을 화면에 필요한 크기까지만** 내보내기. 그쪽은 업로드 시 1920px WebP 로
  다시 인코딩합니다. 우리는 Cloudinary 변환과 Next.js 이미지 최적화로 같은
  효과를 냅니다.

가져오지 않은 것

- **회원 전용 읽기의 캐시**. 게시판·예약·마이페이지는 그대로 데이터베이스까지
  갑니다. 스무 명 규모에서는 캐시로 얻는 것보다 남의 화면에 오래된 값이 보이는
  위험이 큽니다. 게시판 목록 조회가 부담이 되면 그때 다시 봅니다.
- **조회수 지연 기록·집계 테이블·야간 배치**. 우리에게는 조회수도 집계 대상도
  없고, Render 무료 인스턴스는 15분 놀면 잠들어 주기 작업을 맡길 수 없습니다.
- **버전 문자열 캐시 무효화**. 24시간 캐시할 만큼 큰 마스터 데이터가 없습니다.
- **BFF 프록시와 파라미터 허용 목록**. 프런트가 API 를 직접 부르는 구조라
  중간 계층이 없습니다.
- **revalidation 묶음 처리(15초 합치기)**. 운영진 저장이 하루 몇 번이라
  합칠 것이 없습니다.

## 배포 순서

1. Neon의 pooled URL을 Render `DATABASE_URL`에 입력합니다. 일반 `postgresql://` URL과 `sslmode=require`도 앱이 asyncpg 형식으로 정규화합니다.
2. Render에 `SESSION_SECRET`, `FRONTEND_URL`, Google OAuth 환경 변수를 입력하고 배포 전에 `alembic upgrade head`를 실행합니다.
